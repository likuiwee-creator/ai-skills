# Skill 编写规范（写给 AI 的施工图）

> 这份文档是给 **Codex / Trae / Cursor / Claude Code / WorkBuddy 等 AI 写 skill** 时读的。
> 读完照着做，就能产出一个规范、可分发、可维护的 skill。
> 本仓库的 `code-selfcheck` 就是按这份规范做的，可以当范例参考。

---

## 一、Skill 是什么（先对齐概念）

**skill = 一个文件夹 + 一份说明书**，让 AI 在合适的时候自动加载一段专用的工作流程和知识。

它不是插件、不是代码包，而是**给 AI 的「操作手册」**。所以判断标准只有一条：
> AI 读完 SKILL.md，能不能不做额外调研就把这件事做对？

做不出来 = 说明书写得不够；读懂了还要现查 = 内容该补进 SKILL.md。

---

## 二、目录结构（强制规范）

```
skill-name/                      # 目录名 = skill 名，全小写 + 连字符
├── SKILL.md                     # 【必需】说明书，唯一必需文件
├── README.md                    # 【可选】给人看的说明（分发、接入、跨工具）
├── LICENSE                      # 【可选】MIT 等，便于公司内分发
├── scripts/                     # 【可选】可执行脚本
│   └── xxx.py / xxx.cjs
├── references/                  # 【可选】详细参考文档（长内容放这，别塞 SKILL.md）
│   └── detailed-guide.md
├── templates/                   # 【可选】要复制的模板文件
│   └── config.yml
└── assets/                      # 【可选】二进制资源（图片、字体等）
```

**硬性规则**
1. 目录名只能用**小写字母、数字、连字符**（`code-selfcheck`），不能用空格、下划线、中文。
2. `SKILL.md` **必须**在 skill 根目录，且**文件名大写 S**（`SKILL.md` 不是 `skill.md`）。
3. 脚本放 `scripts/`、参考资料放 `references/`、模板放 `templates/`——不要平铺在根目录。

## 三、SKILL.md 写法（最关键的部分）

### 3.1 Frontmatter（文件开头，必须有）

```markdown
---
name: code-selfcheck
description: "代码提交前自检。在任何 JS/Node/Python 项目里跑多阶段检查：语法校验、单元测试、c8 覆盖率下限、小程序页面 jest 单测、安全扫描、AI 代码审查。当用户说「提交前自检」「commit 前检查」「装个自检钩子」「代码质检」「覆盖率门禁」时使用。"
agent_created: true
---
```

**字段说明**

| 字段 | 必需 | 说明 |
|---|---|---|
| `name` | ✅ | skill 名，与目录名一致 |
| `description` | ✅ | **决定 AI 何时加载它，最重要** |
| `agent_created` | 可选 | `true` 表示自建内容 |

### 3.2 description 写法（决定触发成败）

这是**唯一**让 AI 判断"要不要用这个 skill"的依据。必须包含三要素：

1. **能力描述**——这个 skill 能做什么事
2. **场景关键词**——用户会怎么说这件事（**必须包含用户实际用的词**）
3. **技术栈/对象**——针对什么文件、什么项目

对比：

| ❌ 差 | ✅ 好 |
|---|---|
| 描述一个代码审查工具 | 「提交前自检」代码质检，覆盖语法校验、单测、覆盖率门禁、安全扫描。当用户说「提交前自检」「commit 前检查」「装个自检钩子」时使用 |
| Extract CTrip bills | 「携程账单明细提取」把携程导出的 xlsx 里「订单明细」sheet 导出成干净对账表。当用户说「提取携程账单」「导出 OTA 订单明细」时使用 |

**技巧**：把你的 skill 的触发词用中文/英文各写几种放进 description，用户怎么说都能命中。

### 3.3 正文结构（推荐骨架）

```markdown
# 一句话标题

一句话说清这个 skill 干什么。

## 何时使用
- 具体场景 1
- 关键词：「...」「...」+ 什么输入

## 执行规则 / 核心原则      ← 有铁律就写这里（如"缺工具不报错"）
1. ...

## 用法
```bash
命令示例
```

## 已知坑（别重复踩）      ← 最有价值的一节，把踩过的坑写下来
1. ...

## 环境
- 依赖什么，怎么装
```

**关键**：**「已知坑」这节是 skill 质量的灵魂**。你踩过的坑写进去，同一个坑就不会被 AI 再踩一遍（也不会被下次的你再踩一遍）。

## 四、脚本编写规范

### 4.1 必须用相对路径引用
```markdown
# ✅ 正确：留占位符，让调用方替换成实际路径
python "<skill_dir>/scripts/extract.py" "输入.xlsx"

# ❌ 错误：写死某台机器的路径
python "C:/Users/xxx/skills/xxx/scripts/extract.py"
```

### 4.2 依赖要写清
在 SKILL.md 的「环境」一节明确列出：
- 第三方依赖（`pip install xxx` / `npm i xxx`）
- 外部服务/密钥（如需 API key，说明从哪个环境变量读）

### 4.3 脚本要做到「健壮但不啰嗦」
- **不要因为工具没装就报错退出**——要跳过并提示（否则换台电脑就崩）
- 关键流程加 `try/catch`，错误信息要可读
- 有 CLI 参数就给 `--help`

## 五、自检清单（写完对照检查）

- [ ] 目录名是全小写+连字符，与 `name` 一致
- [ ] `SKILL.md` 在根目录，文件名大写 S
- [ ] frontmatter 有 `name` 和 `description`
- [ ] `description` 含**能力 + 场景关键词 + 技术栈**
- [ ] 正文有「何时使用」章节
- [ ] 命令用 `<skill_dir>` 占位符，没写死绝对路径
- [ ] 有「已知坑」章节（写清踩过的坑）
- [ ] 依赖和安装方式写清了
- [ ] 脚本不因缺工具而硬失败

## 六、怎么分发（AI 常被问到）

WorkBuddy/Claude Code 的 skill 市场目前**只读**（只能搜索安装，不能上传自己的 skill）。所以分发走这几条路：

| 方式 | 怎么弄 | 适合 |
|---|---|---|
| **git 仓库** | skill 目录本身做成 git 仓库，同事 clone 到自己的 skills 目录 | 团队协作（推荐） |
| **zip 包** | 直接发文件夹压缩包 | 零门槛给个人 |
| **写进项目** | skill 放项目 `tools/` 目录，随项目 clone | 与项目强相关 |
| **CI 门禁** | 把脚本放仓库 CI，不依赖 skill | 强制执行（唯一不靠个人环境的） |

> **认知**：skill 是「个人/本机能力」，想强制全员执行必须落到 **CI**（仓库里的脚本）。两者可并存——本地钩子用 skill，CI 用仓库脚本，逻辑同一份。

## 七、给 AI 的直接指令模板

把这个模板填好发给 Codex/Trae/Cursor 等 AI，它们就能照着写出规范的 skill：

```
请按 skill 规范帮我写一个 skill，要求：

- skill 名：<name>
- 用途：<一句话说清能做什么>
- 触发词（用户可能会这么说）：<列出 5-8 个中英文关键词>
- 脚本：<描述脚本要做什么、输入输出、依赖什么>
- 已知坑：<把踩过的坑列出来，没有就写"暂无">

规范要求（必须遵守）：
1. 目录 <name>/，内含 SKILL.md，frontmatter 含 name + description
2. description 必须包含：能力描述 + 触发关键词（用户可能说的话）
3. 正文含「何时使用」「执行规则」「用法」「已知坑」「环境」章节
4. 脚本放 scripts/，参考文档放 references/，模板放 templates/
5. 命令用 <skill_dir>/... 占位符引用脚本，禁止写死绝对路径
6. 脚本不因依赖缺失而硬失败，要跳过并提示
```
